## 1. 低风险、可直接做

### 1.1 关键词列表的嵌套滚动会把滚动接力给页面  ★建议优先

- **证据**：`#customKeywordsContainer` 实测 `overscroll-behavior: auto`，
  且它**真的溢出**（456px 内容 / 168–224px 视窗）；内容区 `overscroll-behavior: contain`。
- **问题**：鼠标停在关键词列表里滚到底，滚动会继续传递给外层/页面。
  同一脚本的导航面板滚动区用的是 `contain`（见 `#mgga-nav-dock > .mgga-nav-dock-body`），
  两处行为不一致。
- **改法**：给 `#customKeywordsContainer` 补 `overscroll-behavior: contain`（一行）。
- **✅ 已落地**（2026-09-23，`docs/fixes/2026-09-23-settings-panel-audit-landing.md`）。
  **但"接力给页面"这个说法在落地取证时被更正**：页面那层轮不到 —— 祖先链是
  `kw → .color-picker-content → 页面`，而内容区自己早就有 `contain`，中间就截断了。
  单独压视口（1280×520，逼面板限高、内容区必然溢出）实测量到真正的承接者：

  | 列表滚到底再多滚 10 轮 | 改前 | 改后 |
  | --- | --- | --- |
  | 内容区 `scrollTop` | 0 → **7**（被带动） | 0 → **0** |
  | 页面 `window.scrollY` | 0 | 0 |

  ⇒ 这条的价值是"看关键词列表时不把整个面板的内容区滑走"，不是"防整页乱滚"。
  另：1280×896 下内容区并不溢出 ⇒ 在主探针里这条**测不出差异**，别据此认为它无效。

### 1.2 `.button-row` 的 `margin-top` 有两份，CSS 那份改不动

- **证据**：CSS `.button-row { margin-top: 0.75em }`，而模板里写死
  `<div class="button-row" style="margin-top: 1em;">` —— 内联胜出。
- **问题**：想调按钮行上方间距时改 CSS 无效，是典型的"改了没反应"陷阱。
- **改法**：删掉内联那份，让 CSS 单独负责（顺带和 `padding-top: 0.35em` 一起理一次）。

### 1.3 三个对话框按钮的配色是硬编码，且没有深色变体

- **证据**：实测 `重置 rgb(255,107,107)` / `取消 rgb(0,123,255)` / `确认 rgb(255,165,0)`，
  文字色分别是白/白/黑；样式表里 `#007bff`、`#ffa500`、`#ff6b6b` 只出现一次、
  **没有** `@media (prefers-color-scheme: dark)` 覆盖。
- **问题**：刚把标题栏统一到 GitHub 的 muted 语义色，这三颗按钮仍是 Bootstrap 时代的
  亮蓝/亮橙/亮红，深色面板上尤其突兀；且"确认"用橙色、"取消"用蓝色，与常见语义
  （确认=primary、取消=neutral、重置=danger）相反。
- **改法**：换成 Primer 语义色（`--fgColor-onEmphasis` / `--bgColor-danger-emphasis` 等），
  或至少补一套深色变体。**需要用户拍板**（会明显改变观感）。

### 1.4 三条外部取色库适配是死代码

- **证据**：`panel._pickr` / `panel._huebee` / `panel._spectrum` 全文**只被读取、从未赋值**
  （第 1823–1831 行），`window.Pickr` / `Huebee` / `$` 在脚本里也没有任何加载逻辑
  ⇒ 三个分支恒不执行；配套的 `.pcr-app` / `.huebee` / `.sp-container` 三条 CSS
  （第 1713–1724 行）同样永不生效。
- **改法**：整段删除（约 20 行），留下内置取色器一条路径。

### 1.5 行的节奏差 1.39px

- **证据**：前三行 22.39px、后两行 21px（同一份 `.color-picker-row`）。
  差异来自行内最高的子项：带颜色块的行走 `.color-button`（2em × 0.8em 字号 = 22.4px），
  不带的行走 `.color-toggle-btn`（1.8em = 20.16px）。
- **改法**：给 `.color-picker-row` 一个统一 `min-height`（或用同一套 `em` 尺寸），
  节奏即可对齐。纯观感项。

### 1.6 `#customKeywordsContainer` 的关键尺寸写在模板内联样式里

- **证据**：模板里 `style="max-height: min(16em, 28vh); overflow-y: auto; margin-bottom: 0.5em;"`
  —— 与样式表混用（同屏还有 `.button-row` 的 `margin-top: 1em`）。
- **问题**：主题化、统一滚动条、响应式调整都得去模板里改，且优先级比 CSS 高。
- **改法**：下沉到样式表（注意别重蹈 1.2 的覆辙）。

## 2. 需要设计与决策的项

### 2.1 面板宽度在宽屏上不增长

- **证据**：1280 宽与 2560 宽下 `css width` 都是 `280px`（`min(20em, calc(100% - 2em))`
  + 字号固定 14px ⇒ 恒定 280px）。
- **取舍**：它是"贴左侧的抽屉"，窄一点本身合理；但 4K 全屏下 280px 面板 + 14px 字号
  确实偏小，而悬浮球这轮已经改成了 vmin 自适应 —— 球会变大、面板不变，**两者开始脱节**。
- **可选方案**：① 宽度改 `min(24em, calc(100vw - 2em))`；② 让尺寸变量跟球一致地用
  `clamp()`（宽度/字号整体缩放）。②更彻底，但会牵动所有 em 尺寸，需要眼睛复核。

### 2.2 滚动条风格与导航面板不一致（声明层面）

- **证据**：设置面板的 CSS 里 `::-webkit-scrollbar` 出现 **0** 次；
  导航面板有 10+ 条（隐藏步进箭头、透明轨道、4px 视觉厚度、hover 变实）。
- **⚠️ 未取证的部分**：本机 Chrome（headless）用的是 **overlay 滚动条**，
  实测两处的 `offsetWidth − clientWidth` 都是 **0**，所以**看不到**视觉差异。
  只有在"系统/浏览器设置为始终显示滚动条"、或 Firefox 这类环境里才会露出经典粗滚动条
  （带上下箭头）—— 那时两处观感会打架。
- **改法**：把导航面板那套滚动条规则（含 `@supports` 的 Firefox 分支）抽成可复用的
  一段，同时挂到 `.color-picker-content` 与关键词列表上。**抽公共段之前先确认观感**。

### 2.3 面板内仍有 unicode 字形（方向上的不一致）

- **证据**：开关按钮 `✓`/`✕`（第 2393 行）、内置取色器"清除"按钮 `✕`（第 1879 行）、
  关键词删除/恢复按钮。
- **说明**：本轮用户只要求**悬浮球**改 SVG（已完成）。这些文字按钮用字形其实可接受
  （在 Windows 上 ✓/✕ 由字体渲染，比 emoji 可控），但若要彻底统一到"图标用 SVG"，
  这是下一批工作面。
- **✅ 已实施（2026-09-23，用户拍板"全做"）**：面板内全部状态字形已换成 SVG ——
  对勾 / 叉号 / 撤销三枚 path 与 `githubMarkSvg` 同源，尺寸走 CSS 的 `1em`，
  跟随各处字号自动缩放（0.8em 开关 / 14px 关闭 / 0.85em 清除 / 0.9em 关键词按钮）。
  落地记录与几何取证见 `docs/fixes/2026-09-23-unicode-to-svg.md`。
  ⚠️ 关键约束：**关闭控件与清除按钮是"靠字形撑高"的** —— 它们的盒高 = `line-height`
  撑出的行盒 + padding，所以图标必须留在行内（只给 `vertical-align`，**不能**
  `display:block`），否则行盒塌成图标自身的 `1em`，按钮与两处标题栏会一起矮 2.8px。
  开关按钮与关键词按钮的盒子是定值（`1.8em` / flex 居中），换图标零位移。

### 2.4 两套面板仍是两份实现

- 现在已共享的：`--mgga-fab-size`、`--mgga-fab-icon`、`@keyframes mgga-fab-pop`、
  `FAB_GEAR_PATH`、`GITHUB_MARK_PATH`、关闭按钮的尺寸四件套（靠闸门成对锁死）、
  **滚动条样式**（本轮 §2.2 抽成 `immersiveScrollbarCss()` 生成器：
  导航面板传 1 个宿主、设置面板传 2 个）、**面板基准字号** `--mgga-panel-font`（§2.1）。
- 仍未共享的：面板外壳（定位 / 进出场 / 标题栏结构）、展开态同步逻辑。
- **2026-09-23 决定（用户拍板）：不做整体的"抽面板外壳原语"。** 判据三条：
  ① 本清单 §2.2 那一条（滚动条）已经完成，剩下的"外壳"不是同一层的东西；
  ② 两套面板的**建面范式不同** —— 导航面板是 `createElement` 手搭 DOM（带
  `role`/`aria`/`data-expanded`/`data-mgga-mutation-guard`）+ `NAV_DOCK_STRUCT_VER`
  结构版本号 + 三处版本校验触发重建；设置面板是 `buildSettingsDialogHTML()` 返回
  HTML 串 + `dialog.innerHTML` 一次性灌入。要抽原语得先把这两种范式统一，属重构而非整理；
  ③ 会拆掉 4 条「成对闸门」（关闭控件 / 两处标题栏等高 / 两处标题栏顶边 / 两处关闭控件
  同套样式）—— 这两套面板今天的不对称，正是被这些闸门**强制挡着**的，抽原语时若抽象
  没写好，反而会把不对称引进来。而它能省的是"每加特性改两处"，本轮 4 条改动里只有
  2 条属于这种情况，触发条件（后续还要在这两个面板上迭代）目前也不成立。
- **旧记录（已过期，保留以便追溯）**：本节曾把「滚动条样式」列为未共享项 ——
  该条已由 §2.2 关闭。
- **建议**：如果后续确实要在这两个面板上密集迭代，抽一个"面板外壳"原语（结构 + 定位 +
  进出场 + 标题栏 + 滚动条），把这轮新增的几个变量一起纳进去；**否则每加一个特性都要
  改两处**（本次 4 条改动里有 2 条就是"两处成对"的活）。
