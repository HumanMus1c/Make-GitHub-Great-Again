# 设置面板"可视标题栏"与导航栏对齐（面板顶边 → 分割线）

- **日期**：2026-09-23
- **版本**：v2026.9.23（**未改动版本号** —— 用户已明确要求后续改进不再变更版本号）
- **回滚点**：`snapshot-titlebar-vcenter-20260923`（commit `b5e4689`）
  ⇒ `git reset --hard b5e4689` 可精确回到本次改动之前
- **改动面**：`Make-GitHub-Great-Again.js` 一行 CSS（`.color-picker-dialog` 的 `padding`）
  + 两处注释 + `tools/smoke-load.js` 一条新闸门

## 1. 用户反馈

> 后续改进不再变化版本号：
> Release页面设置面板的标题栏高度仍然和导航栏标题不一致，并且没有再标题栏内垂直居中。

上一版（`b5e4689`）已经把两处 `.header` 的高度对齐到 29.8px，**真机复测也是 29.8px vs 29.8px**，
所以这次必须先把"用户量的到底是什么"弄准，否则会照着错的靶子改。

## 2. 根因：用户量的不是 `.header`，而是"面板顶边 → 分割线"这段可视区

真机细粒度探针 `.workbuddy/probe/diag-titlebar-fine.js`（本次新建）在仓库首页量导航面板、
在 `/releases` 页量设置对话框，同视口 1280px：

| 指标 | 导航面板 | 设置面板（改前） | 差 |
| --- | --- | --- | --- |
| 面板自身 border-top | 1px | 1px | 0 |
| 面板自身 padding-top | **6px** | **17.5px**（`1.25em`） | +11.5px |
| **面板顶边 → 标题栏顶边** | **7px** | **18.5px** | **+11.5px** |
| `.header` border-box 高 | 29.8px | 29.8px | 0（上一版已对齐） |
| **可视标题栏高（顶边 → 分割线）** | **37.8px** | **49.3px** | **+11.5px** |
| 标题盒中心 − 可视区中心 | +0.49px | **+6.25px** | 偏下 5.75px |

两个症状同一个根因：

1. **"高度仍然不一致"** —— `.header` 一样高，但标题栏**上方**多出一条 `1.25em − 6px = 11.5px`
   的空带（设置对话框自身的 `padding`），于是用户眼里"从面板顶边到分割线"这段可视标题栏
   仍然比导航栏高一截。上一版只修了 `.header`，这个父容器层面的差距原封不动 ⇒ 用户看到"没变"。
2. **"没有在标题栏内垂直居中"** —— 设置面板里标题上方留白 20.5px（1px + 17.5px + 2px）、
   下方只有 7px（6px + 1px 边框），标题在这段可视区里明显偏下（实测 +6.25px）。

顺带排除：`.header` 的 `align-items: center` 一直生效（探针里 `display: flex` /
`align-items: center` 都在，"上下留白差 0px" 也证明内容在 padding 盒内是居中的）；
`overflow: hidden`、`container-type` 都没参与这件事。

## 3. 修复

```css
.color-picker-dialog {
  /* 顶部 6px = 导航面板 #mgga-nav-dock 的面板内边距 ⇒ 两处「顶边 → 标题栏顶边」
     都是「1px 边框 + 6px」，可视标题栏高度因此完全相同 */
  padding: 6px 1.25em 1.25em;   /* 原：padding: 1.25em */
}
```

左/右/下仍是 `1.25em`（内容区需要的呼吸），**不参与标题栏高度**。

### 一个刻意保留的取舍：为什么**不**把上下 padding 改成对称的 4px/4px

直觉会想"要让内容垂直居中，就该把 `padding: 2px 4px 6px` 改成对称的 `4px`"。实测反了：

- 眼睛判的居中，是内容相对**可视区**（面板顶边 → 分割线）中心的位置，不是相对 `.header`
  自己那个盒子的中心；
- 面板自己在标题栏上方已经贡献了 7px，所以 `.header` 的 2px/6px 不对称恰好把内容摆到
  可视区中心（实测 **+0.5px**，导航栏 +0.49px）；
- 若改成 `4px/4px`，`.header` 内部是正了，但**两处会一起偏下 3.5px**（可视区中心偏 +3.5px），
  反而更像"没居中"。

⇒ 保留导航栏那套 `2px 4px 6px`，**标准本身不动**，只把父容器的顶部内边距拉平。

### 4.3 闸门为什么必须锁"父容器"

上一版的静态闸门只锁两处 `.header` 自己的声明（padding / margin / 边框 / 字号 / 关闭控件），
**对这次的真实差异是全绿的** —— 断言覆盖不到"标题栏上方还有多少空隙"，所以修与不修它都过。
现新增一条：取 `.color-picker-dialog { … }` 与 `#mgga-nav-dock { … }` 两个基座规则的
`padding` 首值（用带 guard 的 `indexOf` + 必须命中的 `position: fixed` 防锁错规则），
断言"两处相等且 = 6px"。

- **Firefox / Safari** 未测。本改动只是把顶部内边距由相对单位 `1.25em` 换成绝对值 `6px`，
  不涉及新特性，理论上只会更稳。
- **深色系统主题**未测（本次真机跑的是浅色）；对话框的深色配色由
  `@media (prefers-color-scheme: dark)` 提供，与 padding 无关。
- **极窄视口（≤320px）**未重跑：改的是纵向内边距，与视口宽度无关。
- 其它仓库（vscode / kubernetes 等）未复测；`padding` 与仓库内容无关，风险低。
- 用户主观观感未复核 —— 上面三项几何指标是客观判据，但"看着一样了"要用户确认。

## 6. 判据沉淀

- **面板类 UI 的"高度"要连父容器的 border + padding 一起量**：本次的 11.5px 差异全部来自
  `.color-picker-dialog` 自己的 `padding`，只量 `.header` 会得出"已经一样了"的错误结论
  （上一版就是这么误判的）。
- 可见性/几何类断言必须**量用户眼里的那段区域**（面板顶边 → 分割线），而不是内部元素的
  border-box；探针输出里为此专门加了 `gapAbove` / `bandHeight` / `bandCenterErr` 三个字段。
- "垂直居中"要区分**相对 `.header` 盒**还是**相对可视区**；二者会给出相反的最优解
  （对称 padding vs 2/6 不对称 padding）。以人眼看到的为准。
